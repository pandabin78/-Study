# .lib(Static Library)
>**.lib(정적 라이브러리, Static Library)**는 C/C++ 등에서 소스 코드를 컴파일하여 생성된 object 파일들을 하나로 묶어둔 바이너리 파일 아카이브입니다.\
소프트웨어 위기를 극복하기 위한 CBD(컴포넌트 기반 개발) 및 재사용성의 초기 형태이며, 프로그램 빌드 시 최종 실행 파일(.exe 등) 내부에 코드가 완전히 병합되는 특징을 가집니다.
### 💡 실생활 예시
> 밀키트(정적 라이브러리): 요리 재료와 양념이 완벽히 섞여서 포장된 밀키트입니다. 음식을 완성(빌드)할 때 밀키트 전체를 냄비(실행 파일)에 넣고 끓여버립니다. 완성이 되면 밀키트 봉지는 사라지고, 하나의 요리 안에 부품들이 완전히 녹아들어 일체가 됩니다.
### 🛠️ 정적 라이브러리의 핵심 작동 방식
>.lib 파일은 프로그램의 생성 과정 중 링킹(Linking) 단계에서 결합합니다.
- 컴파일 (Compile)
    >개발자가 쓴 .cpp 코드가 컴퓨터가 이해하는 .obj 파일로 바뀝니다.
- 정적 링크 (Static Linking)
    >링커(Linker)가 내가 쓴 .obj 파일과 외부의 .lib 파일을 하나로 합쳐서 하나의 최종 .exe 실행 파일을 뽑아냅니다.
- 실행 (Runtime)
    >실행 파일 내부에 이미 라이브러리 코드가 포함되어 있으므로, 실행 시점에 외부 파일에 의존하지 않고 단독으로 작동합니다.
### 🚀 정적 라이브러리의 장점과 단점
>현대 개발에서 동적 라이브러리(.dll)와 비교했을 때 가지는 뚜렷한 장단점입니다.
#### 👍 장점
- 빠른 실행 속도
    >실행 중에 외부 파일을 찾아서 메모리에 올리는 과정이 없습니다. 이미 내부에 코드가 존재하므로 호출 오버헤드가 없어 속도가 빠릅니다.
- 단독 배포 용이 
    >최종 실행 파일(.exe) 하나만 유저에게 전달하면 끝납니다. ".dll 파일이 없어 프로그램을 실행할 수 없습니다" 같은 런타임 오류가 발생하지 않습니다.
- 소스 코드 보안
    >로직을 기계어로 컴파일하여 배포하므로, 원본 소스 코드를 외부에 유출하지 않고 기능만 안전하게 공유할 수 있습니다.
#### 👎 단점
- 실행 파일 용량 증가
    >여러 프로그램에서 동일한 .lib를 사용한다면, 각 프로그램의 파일마다 중복된 코드가 통째로 박히기 때문에 디스크 공간 낭비가 심해집니다.
- 수정 및 업데이트 불편
    >라이브러리 내부에 버그가 있어 단 한 줄만 수정하더라도, 그 라이브러리를 쓰는 **모든 실행 파일들을 다시 컴파일하고 다시 빌드(재링킹)**해서 배포해야 합니다.
### 🎮 유니티(Unity)와 C# 환경에서의 .lib
- C# 환경의 대체재
    >C#이나 유니티(Managed 환경)에서는 .lib를 직접 사용하지 않습니다. \
    대신 그 역할을 규칙이 잘 정의된 **.dll(클래스 라이브러리)**이나 NuGet 패키지가 대체합니다.
- 유니티 네이티브 플러그인
    >하지만 유니티에서 C++ 기반의 고성능 엔진(예: 물리 연산, AI, OpenCV)을 연동해야 할 때는, C++로 만든 .lib나 .dll을 유니티 프로젝트 내부의 Plugins 폴더에 넣어 네이티브 플러그인 형태로 호출하여 사용하기도 합니다.
