# 코드 스멜
>코드 스멜(Code Smell)은 프로그램 소스 코드에서 더 심각한 버그나 품질 저하(유지보수의 어려움)로 이어질 가능성이 높은 '나쁜 징후'를 뜻합니다. \
리팩토링의 창시자 마틴 파울러(Martin Fowler)가 대중화한 용어로, 당장 컴파일 에러가 나거나 실행이 안 되는 '버그'는 아니지만, 코드를 수정하고 확장하기 어렵게 만드는 잠재적 위험 요소를 의미합니다. \
이전에 우리가 다루었던 강한 결합도, 추상화 부재, 잘못된 CBD 설계 등이 누적되면 코드 스멜이 진하게 풍기기 시작합니다.
### 🎮 유니티(Unity) 개발에서 흔히 발생하는 3대 코드 스멜
>유니티 프로젝트가 커질 때 개발자들을 괴롭히는 대표적인 나쁜 징후들과 C# 코드 예시입니다.
1. 거대 클래스 (Large Class / 신의 객체 - God Object)
    >하나의 스크립트가 게임의 너무 많은 것을 알고 제어하는 현상입니다. 응집도가 낮고 결합도가 극도로 높아집니다.
    - 징후
        >PlayerController.cs 파일 하나가 3,000줄이 넘고, 이동/애니메이션/사운드/체력/인벤토리/UI 업데이트를 혼자 다 처리하고 있을 때.
    - 해결책
        >CBD(컴포넌트 기반 개발) 사상에 맞게 PlayerMovement, PlayerAudio, PlayerHealth 등으로 기능을 쪼개어 조립해야 합니다.
2. 기능 편애 (Feature Envy)
>어떤 메서드가 자신이 속한 클래스의 변수보다, 다른 클래스의 데이터를 더 많이 참조하고 조작하는 현상입니다. (내용/공유 결합도가 높아지는 원인)
- ❌ 코드 스멜 상태: 플레이어가 데미지를 입힐 때, 적의 내부 데이터를 직접 가져와 연산합니다.
```csharp
public class Player : MonoBehaviour
{
    public void Attack(Enemy enemy)
    {
        // Player가 Enemy의 내부 데이터(HP, 방어력)를 편애하여 직접 계산함
        int damage = 50 - enemy.armor; 
        enemy.currentHp -= damage; 
    }
}
```
- 🟢 리팩토링 후 (추상화 적용): 데이터를 가진 객체가 스스로 일하게 만듭니다.
``` csharp
public class Player : MonoBehaviour
{
    public void Attack(IDamageable target)
    {
        target.TakeDamage(50); // 깔끔한 약한 결합
    }
}
```
3. 산탄총 수술 (Shotgun Surgery)
    >하나의 요구사항(기능)을 수정했는데, 그것과 연관된 수많은 스크립트를 동시다발적으로 수정해야 하는 현상입니다. 코드가 온 사방에 파편화되어 결합해 있을 때 발생합니다.
    - 징후
        >게임 내 '재화(Gold)' 단위를 int에서 float로 바꾸려고 하더니 상점, 인벤토리, UI, 몬스터 보상 등 20개가 넘는 C# 파일에서 에러가 터져 일일이 수정해야 할 때.
    - 해결책
        >해당 데이터와 로직을 한 곳으로 모으는 응집도 높은 클래스를 설계하거나, 인터페이스를 통해 접근을 단일화해야 합니다.
### 🧪 대표적인 코드 스멜 종류 요약
- 중복 코드 (Duplicated Code)
    >똑같은 코드가 여러 곳에 복사·붙여넣기 되어 있는 상태 (수정할 때 하나라도 빼먹으면 버그 발생).
- 긴 메서드 (Long Method)
    >한 메서드가 너무 많은 일을 해서 코드가 수백 줄에 달하는 상태 (읽기 어렵고 재사용 불가).
- 데이터 뭉치 (Data Clumps)
    >int x, int y, int z 처럼 항상 3~4개의 변수가 여러 메서드에 세트로 붙어 다니는 상태 (하나의 구조체나 클래스로 묶어야 함).
- 강박적 기본 타입 사용 (Primitive Obsession)
    >돈, 좌표, 전화번호 등 의미 있는 데이터를 단순히 int, string 같은 기본 타입으로만 처리하려는 경향.
### 🚀 코드 스멜을 제거하는 방법: 리팩토링(Refactoring)
>코드 스멜이 난다고 해서 프로그램을 처음부터 다시 짤 필요는 없습니다. \
소프트웨어의 겉으로 보이는 기능(결과)은 그대로 유지한 채, 내부의 구조만 깨끗하게 개선하는 '리팩토링'을 주기적으로 수행하면 됩니다.\
유니티 개발 과정에서 내 코드에 스멜이 나는지 점검해 보고 싶으신가요? 현재 작성 중인 코드 중에서 "이 부분이 좀 찝찝한데 스멜일까요?" 하는 구현부를 보여주시면 리팩토링 방향을 제안해 드릴 수 있습니다.
