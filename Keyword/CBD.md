# CBD(Component Based Development)
>CBD(컴포넌트 기반 개발, Component Based Development)는 소프트웨어를 처음부터 다 만드는 것이 아니라, 독립적인 기능을 수행하는 소프트웨어 모듈(컴포넌트)들을 마치 레블 블록처럼 조립하여 새로운 애플리케이션을 구축하는 개발 방법론입니다.\
1990년대 후반 소프트웨어의 재사용성을 극대화하여 개발 생산성을 높이고 소프트웨어 위기를 극복하기 위해 등장했습니다. \
이전에 다루었던 추상화와 다형성의 개념이 소스 코드 수준을 넘어, '배포 가능한 독립적 제품(부품)' 단위로 확장된 개념이라고 보시면 됩니다.
### 💡 실생활 예시
- PC 조립
>컴퓨터를 만들 때 메인보드, CPU, 그래픽카드를 직접 설계하고 납땜하지 않습니다. \
이미 시장에 완성품으로 나와 있는 부품(컴포넌트)들을 사서 규격(인터페이스)에 맞게 꽂기만 하면 고성능 PC가 완성됩니다.
### 🎮 유니티(Unity) 엔진과 CBD의 관계
>사실 유니티를 사용해 보셨다면 이미 CBD 방식을 완벽하게 경험하신 것입니다. \
유니티의 핵심 아키텍처인 **'컴포넌트 패턴(Component Pattern)'**이 바로 CBD의 사상을 그대로 게임 엔진에 녹여낸 것이기 때문입니다. 
- ❌ CBD가 없는 기존 개발 방식 (상속의 한계)
    >Player 클래스와 NPC 클래스가 물리 엔진과 오디오 기능이 필요하다면 부모 클래스로부터 거대한 상속 구조를 만들어야 했습니다.\
    이 방식은 구조가 복잡해지면 유연성이 떨어집니다.
- ⭕ 유니티의 CBD 방식 (컴포넌트 조립)
    >유니티에서는 빈 게임 오브젝트(GameObject)를 만들고, 검증된 컴포넌트들을 마우스로 드래그 앤 드롭하여 조립합니다.
    - 움직임이 필요하면? ➡️ Rigidbody, Collider 컴포넌트 추가
    - 소리를 내고 싶다면? ➡️ AudioSource 컴포넌트 추가
    - 내가 만든 기능을 넣고 싶다면? ➡️ C# 스크립트(컴포넌트) 추가
### 🚀 CBD의 주요 특징과 장점
- 높은 재사용성(Reusability)
    >한 번 잘 만들어둔 컴포넌트(예: 로그인 모듈, 결제 모듈, 캐릭터 이동 컴포넌트)는 다른 프로젝트나 시스템에서도 그대로 가져다 쓸 수 있습니다.
- 유지보수 용이성
    >특정 기능에 문제가 생기면 전체 시스템을 수정할 필요 없이, 해당 컴포넌트만 쏙 빼서 수정하거나 새것으로 교체(플러그 앤 플레이)하면 됩니다.
- 품질 향상 및 기간 단축
    >이미 철저하게 테스트를 거쳐 검증된 컴포넌트들을 조립하기 때문에, 소프트웨어 초기에 발생하는 잔버그가 크게 줄어들고 전체 개발 기간(Time-to-Market)이 비약적으로 단축됩니다. 
### ⚠️ CBD의 단점과 한계
- 컴포넌트 인증/테스트 비용
    >범용적으로 쓸 수 있는 완성도 높은 부품을 만드는 설계 단계 자체에 많은 시간과 고도의 기술력이 필요합니다.
- 타사 컴포넌트 의존성
    >외부에서 구매하거나 가져온 컴포넌트 내부의 보이지 않는 독자적인 로직(블랙박스) 때문에 성능 저하나 호환성 문제가 발생했을 때 디버깅이 어려울 수 있습니다.
