# DLL
>.dll(동적 연결 라이브러리, Dynamic Link Library)는 프로그램이 실행되는 시점(Runtime)에 필요할 때만 메모리에 로드되어 연결되는 공유 라이브러리 파일입니다. \
마이크로소프트 윈도우(Windows) 운영체제의 핵심 아키텍처 중 하나입니다. \
이전에 다루었던 .lib(정적 라이브러리)가 빌드할 때 실행 파일 내부에 코드를 완전히 박아버린다면, .dll은 "코드는 밖에 따로 빼두고, 실행할 때 필요할 때만 불러다 쓰는" 방식입니다. \
프트웨어 공학 관점에서 결합도를 낮추고 재사용성을 극대화한 CBD(컴포넌트 기반 개발)의 대표적인 형태입니다.
### 💡 실생활 예시
>스트리밍 서비스(동적 라이브러리): 영화를 내 컴퓨터에 다운로드(정적 라이브러리) 받아두는 것이 아니라, 넷플릭스(DLL)를 켜서 보고 싶은 영화를 그때그때 실시간으로 재생(동적 연결)하는 방식입니다. \
컴퓨터의 용량을 거의 차지하지 않고, 새로운 영화가 업데이트(라이브러리 수정)되어도 유저는 영화를 다시 다운받을 필요가 없습니다.
### 🛠️ 동적 라이브러리의 핵심 작동 방식
>.dll 파일은 프로그램의 생성 과정 중 빌드가 끝난 후, 실행 단계에서 결합합니다.
- 빌드 단계
    >링커(Linker)는 실행 파일(.exe) 내부에 라이브러리의 실제 코드를 넣지 않습니다. 대신 "이 함수는 외부 ABC.dll 파일의 몇 번째 위치에 있다"라는 주소록(가져오기 주소 테이블, IAT)만 기록합니다.
- 실행 단계 (Runtime)
    >프로그램이 켜지다가 해당 함수의 호출부를 만나면, 운영체제(OS)가 하드디스크에서 ABC.dll 파일을 찾아 메모리(RAM)에 로드하고 연결합니다.
- 공유
    >다른 프로그램들이 동시에 같은 ABC.dll을 사용하더라도, 메모리에는 딱 한 번만 올려두고 주소만 공유해서 함께 씁니다.
### 🚀 동적 라이브러리의 장점과 단점
#### 👍 장점
- 실행 파일 용량 및 메모리 절감
    >코드가 내부에 박히지 않아 실행 파일 용량이 매우 작아집니다. \
    또한, 여러 프로그램이 하나의 DLL을 공유하므로 RAM 공간을 효율적으로 씁니다.
- 유지보수 및 업데이트 용이
    >라이브러리 내부 로직에 버그가 있어 수정해야 할 때, 실행 파일(.exe)을 다시 빌드할 필요가 없습니다. 오직 문제가 생긴 .dll 파일 하나만 새로 교체하면 모든 프로그램에 즉시 반영됩니다. (플러그 앤 플레이 구조)
#### 👎 단점
- DLL 지옥 (DLL Hell)
    >프로그램이 실행될 때 외부 .dll 파일에 절대적으로 의존하기 때문에, 파일이 삭제되거나 이름이 바뀌면 "~~.dll이(가) 없어 프로그램을 시작할 수 없습니다"라는 치명적인 런타임 크래시가 발생합니다.
- 약간의 호출 오버헤드
    >실행 중에 주소를 찾고 메모리에 연결하는 과정을 거치므로, 아주 미세하게 정적 라이브러리보다 실행 속도가 느릴 수 있습니다.
### 🎮 유니티(Unity)와 C# 환경에서의 DLL
>C#과 유니티 개발자에게 DLL은 떼려야 뗄 수 없는 가장 친숙한 빌드 단위입니다.
- C# 클래스 라이브러리
    >C#에서 코드를 컴파일하면 최종 결과물로 .dll 파일이 나옵니다. (C#은 소스 코드를 기계어가 아닌 중간 언어(IL)로 컴파일하기 때문에 .lib가 존재하지 않고 무조건 .dll 형태로 빌드됩니다.)
- 유니티 에셋 플러그인
    >유니티에서 유료 에셋(예: Odin, DOTween 등)을 구매하여 임포트하면, 원본 소스 코드(.cs) 대신 빌드된 .dll 파일만 들어있는 경우가 많습니다. 이는 소스 코드 유출을 방지하면서 기능만 제공하기 위해 사용됩니다.
- 컴파일 속도 향상 (Assembly Definition)
    >유니티 프로젝트가 거대해지면 코드 한 줄 고칠 때마다 몇 분씩 컴파일 시간이 걸리는 '코드 스멜'이 발생합니다. 이때 기능을 폴더별로 나누어 각각 독립된 .dll(어셈블리)로 빌드되도록 설정(asmdef)하면, 수정된 스크립트가 속한 DLL만 새로 컴파일하므로 빌드 속도가 비약적으로 빨라집니다.
